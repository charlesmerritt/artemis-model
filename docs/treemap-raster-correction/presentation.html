Correcting the TreeMap raster

TreeMap is an imputation, not a measurement. Every ARTEMIS output inherits its errors, so "repair TreeMap" is now an explicit upstream stage rather than an assumption. This is where that correction stands: what is measured and fixed, what is decided but unbuilt, and what is still open.

The object being corrected 02

One whole FIA plot is stamped onto every forested pixel

TreeMap is a 30 m raster of imputed FIA plot identifiers (TM_ID → PLT_CN). It is a map of which plot best matches here — not a map of measured values. Basal area, volume, carbon and the tree list are all carried over from that plot.

How it is built Riley / Houtman lineage

Modified Random Forest imputation via R yaImpute, ~249 trees per LANDFIRE zone (83 per response variable). Each pixel receives the single plot that co-occurs with it most often in the terminal nodes — k = 1, one whole plot per pixel.

Predictors: LANDFIRE EVC/EVH/EVT, disturbance and time-since, terrain, lat/lon, Daymet 1981–2010 normals. Reference: single-condition forested FIA plots, 1997–2022, true unfuzzed coordinates.

Why that shape drives every correction consequence

Because a whole plot is stamped, an error is never a small numeric nudge — it is the wrong tree list over a contiguous block of ground, and it propagates identically through FVS growth, painting, and every summary built on top.

It also means correction has two independent handles: which plot lands where (geography) and how much area each plot gets (allocation). They fail differently and are fixed differently.

The core result 03

Two error channels — and only one of them is correctable by rescaling

Pixel-count expansion (acres ≈ Count × 0.2224) is not the FIA design-based estimator. TreeMap pixel sums diverge from FIA in two separable ways, and the standard fix only touches the first.

(a) Area misallocation correctable

Imputation may paint a plot onto more or fewer pixels than its design weight (EXPNS) warrants. Symptom: forest-type acreages drift away from FIA.

Fix: area-scale by FIA forest-type acres. Detect over-concentration with the pixel-weighted plot distribution and effective sample size.

(b) Within-type attribute bias not correctable that way

Even at exactly the right acreage, the plots chosen inside a forest type can be systematically denser or sparser than the FIA population for that type.

Area-scaling does not touch this. It has to be measured per FORTYPCD and reported, not rescaled away.

Standing rule: TreeMap is validated for mapping and landscape modelling — it is not a substitute for design-based estimates. The QA that decomposes the two channels is 1_FL_FIA_TreeMap_comparison.R (rFIA design-based vs TreeMap pixel-weighted, by BALIVE, TPA_LIVE, live AG carbon). Not yet ported to ARTEMIS.

Correction 1 05

The vintage trap: two TreeMaps on disk, and they do not agree

Prototype scripts labelled outputs TreeMap2022 while reading a TreeMap2020_CONUS.tif path. The two vintages produce different crosswalks — 693 rows vs 688 — and pairing them across is a silent, partial data loss.

The painter now reports coverage for both pairings and auto-selects the better one, so the trap cannot be re-entered silently. 2022 gives 100% stand and 100% pixel coverage.

Still a live hazard: the richer linkage table carrying STAND_ID (output2020/TreeMap_FVS_linkage.csv) is 2020-vintage, 688 rows — it must never be paired with the 2022 raster. Plain painting does not need it, because stand_cn already equals PLT_CN.

Correction 2 06

Three integrity bugs that quietly deleted or scrambled pixels

None of these announce themselves. Each produces a plausible-looking raster that is wrong, which is why they belong in the correction stage rather than in debugging folklore.

Category strings for IDs fixed

terra::rast() auto-loads the TreeMap VAT, so freq() can return active category strings such as ForTypName instead of integer TM_ID values.

Rule: always count on as.int(); never trust VAT display names.

FIA control numbers overflow fixed

PLT_CN exceeds R double precision, so numeric handling corrupts the join key itself — the identifier survives, but points at the wrong plot.

Rule: keep PLT_CN, CN, Stand_CN, StandID as strings end to end.

Label-0 collision fixed + test

skimage's felzenszwalb() labels from 0, unlike slic() (start_label=1). Non-forest was then masked to 0 and vectorisation skipped 0 as nodata — so whichever forest segment happened to be labelled 0 was silently dropped before any measurement.

Recovered: 52 pixels · 4.68 ha · 14 patches. Post-erase forest now matches SLIC exactly (27,806.344 ha).

Correction 3 07

The forest mask lies about recently-cut ground

LANDFIRE EVT is both a TreeMap predictor and our forest mask. It labels some recently clearcut forest as agriculture, grassland or shrubland — so that land is dropped from the forested universe entirely, exactly where harvest just happened.

  • LCMS tree-removal almost never fires here — these pixels were likely cut before the window or reclassified, which is why the mislabel survives.

The feature-engineered run then scores the suspect classes directly. Share of each class estimated to be recently-forest: floodplain shrub 0.81, ruderal grassland 0.41, pasture/hay 0.06.

Read the headline AUC with care. Featsets B and C reach AUC ≈ 1.000, but positives are defined as pre-year forest and negatives as never-forest, and the pre-year embedding encodes exactly that — near-circular, so treat it as an upper bound. Featset A (event embeddings only), AUC 0.994, is the honest appearance-based number. The apply-set fractions are estimates awaiting imagery or field validation.

Sampling fix worth keeping: two-stage decimated→full-res reads took rare-class hit rate from 2/30 to 150/150.

Correction 5 11

The erase layer is deleting forest we are supposed to grow

Today sketch_management_units.py unions stream/BMP buffers, NHD waterbodies and the road-artifact buffer into one erase layer and differences it out. Buffer acres are discarded — neither managed nor grown, simply absent from the projected landscape. That is an under-count of standing volume and carbon, not a conservative choice.

The regime, as decided settled

Grow freely — projected through FVS on the same cycles as everything else.

Never harvested — no entry of any kind, assigned by geometry, unconditional.

Reported as unique buffer polygons — own unit IDs, own rows, own painted pixels. Not dissolved into neighbours, not collapsed into one landscape-wide aggregate.

The accounting identity that has to hold unbuilt

Erase-then-add, so managed and riparian units partition the eligible forest area with no overlap:

Σ managed + Σ riparian ==
(forest mask ∩ parcels) − (waterbodies ∪ road buffer)

The raw forested AOI is the wrong right-hand side: roads run through forest and NHD polygons clip forest pixels at 30 m, so those acres are permanently excluded. Report that excluded area as its own line so the drop stays visible instead of silently absorbing a bug.

Still open: whether buffer polygons are generated once against full hydrography and clipped per county, or rebuilt per county — the current per-county loop would split a buffer straddling a county line into two polygons with unrelated IDs.

Correction 6 12

Keying management to the plot smears the harvest across the county

Growing TreeMap pixels directly is mechanically what the painter already does. But if the regime is keyed to the plot, then managing a plot manages every pixel imputed to that plot, wherever it occurs. TM_ID 2623 alone covers 1,385 pixels — a clearcut would appear as speckle across the whole AOI instead of a contiguous block.

The fix: split the keys design settled

Regime is assigned per pixel, inherited from the management unit the pixel falls in, plus ownership, forest type and riparian class. Contiguity comes from the unit layer.

Trajectories are keyed by (plot_id, regime, site-index bin). The same plot can be clearcut in one unit and untouched in another, because those pixels look up different trajectories.

The unit decides what treatment; the plot decides what tree list.

What it costs watch this

FVS run count becomes unique(plot × regime × SI bin) — bounded by key combinations rather than by pixel or unit count, which is the only form that scales past the pilot.

But every regime parameterisation multiplies it. Keeping the regime library small and discrete, rather than continuously parameterised per unit, is what keeps this tractable statewide.

Open: the distribution rule for unit-level partial-harvest targets across constituent plots, and whether tiny plot slivers inside a unit get dropped below an area threshold.

Per-acre semantics carry through rule

TreeMap stores per-acre densities, never per-pixel totals — and so do the FVS values we paint. Fine for maps, quantiles and pixel-wise change; totals require × pixel acres (900 m² = 0.2224 ac). Aggregations are area-weighted means, never naive pixel means.

Snapshot keying is ragged gotcha

Stands start in different inventory years (1997–2021) but share a projection end year (2076). Absolute mid-run calendar_year is not a synchronised snapshot. The only two anchors common to all 693 stands: years_since_start == 0 and calendar_year == 2076.

Where this leaves us 15

The correction story, in one slide

  • Repair is a stage now — the pipeline starts at a corrected raster; nothing downstream is trusted before it.
  • The mechanical corrections are done — vintage disambiguated (693/693, 100% pixels), identifiers made exact, the label-0 drop closed and tested.
  • The mask problem is measured, not fixed — ruderal grassland is the offender, embeddings are the adjudicator at 0.954 under spatial block CV, and the apply-set fractions still need imagery validation.
  • Segmentation was the negative result that mattered — better shapes, no fewer slivers. The merge is the load-bearing step.
  • Two corrections are decided but unbuilt — riparian acres must stop being erased, and regimes must key to pixels while trajectories key to (plot, regime, SI).
  • One correction has not started — reconciling 1997–2021 plot vintages to the circa-2022 raster, and porting the area-vs-attribute QA that would tell us how big the remaining bias is.
The honest limit: area-scaling can correct where the acres are. Nothing in this stage corrects within-forest-type attribute bias — that can only be measured and reported. TreeMap stays a mapping and landscape-modelling product, never a substitute for design-based FIA estimates.
