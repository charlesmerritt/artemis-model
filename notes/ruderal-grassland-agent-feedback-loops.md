# Agent feedback loops for ruderal grassland rectification

Companion to [[ruderal-grassland-clean-slate]] (`docs/adr/0001-ruderal-grassland-clean-slate.md`).
That ADR deliberately leaves the classifier and generative model unspecified — first-principles,
figure-it-out-as-you-go. This note is about *how* to figure it out: what to build into every stage
so the implementing agent can check its own work by running things and looking at the output,
rather than writing code on faith and waiting for a human review round to find out it's wrong.

The general shape, per stage: a **fast path** (seconds, tiny sample) for exploring many ideas
cheaply, and an **artifact** every run produces that is directly inspectable — a number an agent
can grep, or an image an agent can `Read` and actually look at. Claude Code's `Read` tool renders
PNGs — that's a real second pair of eyes an agent has on its own output, not just assertions.
Use it deliberately.

## Mask stage (LF-EVT 2022 selection)

- `--sample-window`/similar: run against one small georeferenced tile, not the full AOI, while
  iterating on the selection logic.
- Every run writes a PNG chip — the mask overlaid on NAIP true color for a handful of windows —
  so "did I select the right pixels" is answerable by reading an image, before scaling to the
  full AOI where a mistake is expensive to notice.

## Feature stage (multi-year AlphaEarth embeddings)

- Sanity numbers printed/written every run: row count, NaN count, per-row L2 norm (should be ~1.0
  — the existing clearcut/agriculture work already checks this and it caught a real bug class).
- A PCA scatter PNG, colored by whatever weak proxy is available (EVT sub-code, rough patch age),
  even before there's a real label — lets an agent eyeball cluster structure forming (or not)
  before committing to a modeling approach.

## Classifier / generative model stage (unspecified by design — build this in from the start)

- Whatever the model turns out to be, make trying a candidate cheap: a small run folder per
  attempt with its config, its metrics, and one or two figures — the `experiment` skill's shape is
  a reasonable default if nothing simpler fits. The point is that trying five ideas and discarding
  four should be *cheap and recorded*, not a single all-or-nothing commitment. This is the
  exploration side; only promote a run to "the approach" once it's been compared against its
  alternatives, not because it's the first thing tried.
- A cluster/prediction map PNG, plus the same map with NAIP underneath — an agent should be able
  to look at a handful of "confident grass" and "confident clearcut" predictions against imagery
  itself and sanity-check before ever handing a batch to a human reviewer.

## Validation webapp (the review queue)

This is where the interactive loop matters most, since it's UI/UX work and "does this look and
feel right" is not something an agent can verify by reading a return value.

- **Seed data.** A small fixture set (a handful of sample points + their NAIP tiles + fake
  predictions) checked in or generated by a script, so the app boots and has something to review
  without needing a full pipeline run first. Nothing about iterating on the UI should require
  Earth Engine credentials or a completed classifier.
- **Playwright, run by the agent, not just by a human at the end.** A script that launches the
  app, loads the queue, clicks through a few approve/disapprove/ambiguous verdicts, and:
  - screenshots the page at a couple of viewport widths (this *is* the responsiveness check the
    user flagged — an agent can look at a narrow-viewport screenshot and see the layout break
    without a human ever opening a browser),
  - asserts the verdict landed correctly in the database.
  This turns "fix the UI" into a real loop: change CSS/markup → run the script → read the
  screenshot → see if it actually looks better, not just "the build succeeded."
- **A backend smoke test independent of the browser** (a plain HTTP client script hitting the
  API) so a backend bug and a frontend bug are never conflated when something fails.

## Why this belongs in the plan, not just in the code later

Retrofitting inspectability after the fact is expensive — precisely the kind of thing that's easy
to skip under deadline pressure and hard to add once three stages already exist without it. Since
the classifier and even the AOI-scale rollout are staged and iterative by design (5 counties →
Florida → another state; try approaches → pick one), the fast/inspectable path *is* the main way
work gets checked at every stage in between, not an add-on at the end.
